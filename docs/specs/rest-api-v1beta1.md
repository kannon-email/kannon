## Problem Statement

Kannon exposes administration, sending and statistics through legacy Connect/gRPC contracts, without a coherent REST interface or an OpenAPI definition. Integrators encounter inconsistent pagination and response shapes, transport-era names such as message_id for a Batch, and credentials that can either administer everything or only send for one Domain. They cannot retrieve a complete Batch/Delivery history through a public API.

Reliable REST integration requires more than translating RPC names into URLs. Client retries must not send twice, accepted sends must not change when a Template is edited, individual intake refusals must be distinguishable from later Delivery outcomes, and clients need predictable errors, authorization and retention. These improvements must preserve existing API Keys and keep HTTP concerns out of the domain model.

## Solution

Deliver a complete, OpenAPI-first REST API under /v1beta1 for Domain administration, Templates, API Keys, Batch creation and history, Delivery history, statistics and public readiness. Make REST the primary evolving contract while maintaining existing gRPC clients during their transition.

Use one Domain-explicit resource hierarchy for global administrators and Domain credentials. Extend the existing authorization engine with a small five-role catalogue, preserve existing credentials in the same table, and provide reliable Batch intake with transactional persistence, immutable content and required idempotency. Keep implementation lean: reuse existing application modules, persist simple Delivery history, and avoid generic orchestration, projection or pagination frameworks.

19. As a Domain administrator, I want to create, list, read, update and delete Persistent Templates, so that reusable content is manageable through REST.
20. As an integration reader, I want summary lists and separate detail reads, so that listing resources does not download large email bodies.
21. As a sender, I want one Batch creation operation accepting either inline HTML or a Template reference, so that both forms share the same sending contract.

23. As a sender, I want the reserved email variable to mean the actual recipient address, so that personalization cannot redefine it accidentally.
24. As a sender, I want unresolved personalization to reject the affected Recipient inline, so that incomplete messages are not queued for that Recipient.
25. As a sender, I want optional future scheduling, so that I can create a Batch before it should be sent.

27. As a sender, I want accepted content frozen at creation, so that later Template edits or deletion cannot alter a scheduled Batch.
28. As a sender, I want supported attachments with explicit size limits, so that I know whether a request can be accepted.
29. As a sender, I want duplicate attachment names rejected, so that one attachment is not silently replaced by another.
30. As a sender, I want up to 2,000 Recipients in a Batch, so that I can submit bounded multi-recipient work.
31. As a sender, I want valid Recipients accepted even when others are refused, so that one invalid row does not stop all deliveries.
32. As a sender, I want inline refusals to identify the original input index and a stable reason, so that I can reconcile the submitted rows.
33. As a sender, I want an all-refused request to fail without creating a Batch, so that success always means some work was accepted.
34. As a sender, I want later duplicate addresses rejected explicitly, so that one Batch cannot accidentally send twice to the same canonical address.
35. As an operator, I want inline-rejected recipient details excluded from persistence, so that unaccepted inputs do not become stored Delivery history or response-cache records.
36. As a sender, I want Batch and accepted Delivery creation to be atomic, so that infrastructure failure cannot leave a partially accepted operation.
37. As a sender, I want required idempotency keys, so that retrying after a timeout does not create duplicate sends.
38. As a sender, I want concurrent requests using one key to create at most one Batch, so that parallel retries are safe.
39. As a sender, I want changed input with an already-bound key to conflict, so that a retry cannot accidentally become a different send.
40. As a sender, I want validation failures before creation to leave the key reusable, so that I can correct a rejected request.
41. As a sender, I want to recover the same Batch and original intake counts for at least 24 hours, so that a lost creation response can be reconciled without persisting inline refusals.
42. As a sender, I want replay to remain valid after a scheduled timestamp passes, so that idempotency does not depend on retry timing.
43. As a Batch reader, I want to list and read Batches, so that I can inspect accepted work and its current progress.
44. As a Batch reader, I want stable public Delivery identifiers and outcome history, so that I can inspect each accepted Recipient after processing ends.
45. As a Batch reader, I want Batch completion distinguished from universal delivery success, so that a completed Batch does not conceal bounces or failures.
46. As a Batch reader, I want post-intake rejections visible on existing Deliveries, so that these outcomes remain distinct from response-only intake refusals.
47. As a Batch reader, I want late bounces reflected in Delivery outcomes, so that an earlier SMTP handoff is not treated as immutable proof of successful delivery.
48. As a Batch reader, I want a clear 30-day history deadline after processing completion, so that I know how long Batch and Delivery records remain available.
49. As a sender, I want pending and scheduled work protected from history cleanup, so that retention never deletes unfinished work.

59. As a maintainer, I want application and domain types independent of generated HTTP types, so that transport changes do not redefine business rules.
60. As a maintainer, I want existing application modules and test interfaces reused, so that this feature does not introduce unnecessary abstraction layers.

## Implementation Decisions

- **Contract and compatibility.** REST uses OpenAPI 3.1.1 and the /v1beta1 base URL. The approved contract has 21 operations and 48 schemas. It is the source for REST wire types, handler interfaces and documentation, independently of protobuf. Evolve v1beta1 compatibly; breaking changes require another version. New functionality targets REST; gRPC receives necessary fixes and remains available without a removal date. Preserve explicit legacy differences, including authentication, personalization and all-intake-refused behavior.
- **Architecture.** Reuse the existing Domains, Templates, API Keys and Stats application modules. Add the missing high-level Batch creation operation using application-owned inputs, results and errors. REST adapters decode transport shape, authenticate into a Principal, translate values and map results/errors to HTTP. Application operations own authorization, business validation, snapshots, atomic persistence and idempotency. Domain/application interfaces must not import generated OpenAPI types, HTTP/Connect request types or the REST adapter. Persistence implements the interfaces those operations need. Enforce import direction. Do not introduce command buses, per-endpoint factories, redundant pass-through layers or mechanically duplicated models.
- **Resource hierarchy.** Global and Domain credentials share one hierarchy, with Domain explicitly in the path. There is no parallel administrative API. Domain names identify Domains and are immutable. Resource IDs are opaque strings; clients must not parse their structure. JSON fields use snake_case, own IDs use id, and references use names such as batch_id and template_id.

| Method(s) | Path relative to /v1beta1 | Operation |
| --- | --- | --- |
| POST, GET | /domains | Create/list Domains; global admin only |
| GET, PATCH | /domains/{domain} | Read Domain / replace Tracking Policy |
| POST, GET | /domains/{domain}/templates | Create/list Persistent Templates |
| GET, PATCH, DELETE | /domains/{domain}/templates/{template_id} | Read/update/delete Template |
| POST, GET | /domains/{domain}/api-keys | Create/list credentials |
| GET, PATCH | /domains/{domain}/api-keys/{key_id} | Read metadata / revoke credential |
| POST, GET | /domains/{domain}/batches | Create/list Batches |
| GET | /domains/{domain}/batches/{batch_id} | Read Batch |
| GET | /domains/{domain}/batches/{batch_id}/deliveries | List Delivery history; optional status filter |
| GET | /domains/{domain}/batches/{batch_id}/deliveries/{delivery_id} | Read Delivery |
| GET | /domains/{domain}/stats/events | Query retained individual events |
| GET | /domains/{domain}/stats/aggregated | Query Domain counters |
| GET | /health | Public minimal readiness |

- **Five-role RBAC.** Reuse the existing Principal, Role, Grant, Anchor, Action and Guard model. Roles compose on one credential. admin has all authority beneath its Anchor; sender creates Batches; batch-reader reads/lists Batches and Deliveries including recipients; analyst reads individual events and aggregates; metrics-reader reads aggregates only. Template and credential management require admin. A global admin may act for any Domain, including sending, while retaining its own authenticated identity. A Domain admin may issue supported roles only for that Domain. There is no limited-role issuer or generic delegation engine in this beta. Existing sender keys do not gain read access.
- **Credentials without data migration.** Keep the existing api_keys table, existing rows, IDs, hashes, prefixes and secrets. Do not copy, replace, backfill or reissue existing keys. Add only the necessary role metadata in place; absent legacy metadata resolves to sender on the existing Domain. Additive schema support is distinct from a data migration of existing keys. REST accepts the Admin Token and Domain API Keys through Authorization: Bearer. Existing gRPC credential handling stays unchanged. Key creation takes name, supported roles and optional expires_at. Omitted expiry means no automatic expiration; explicit expiry must be future. Roles are immutable. Only creation returns secret; reads never return it. Revocation is an idempotent PATCH setting status to revoked, retains metadata and cannot be reversed. Change powers or rotate by issuing a new key and revoking the old one.
- **Attribution and audit.** Preserve X-Kannon-Attribution as an optional audit claim, not authority or identity replacement. Guard requires attribute on the target; admin has it and the other five-role catalogue entries do not. Preserve existing UTF-8, no-control-character, trimmed nonempty and 256-byte validation. An empty header means absent. Always retain authenticated credential identity. Reuse existing authorization audit behavior rather than adding a second audit subsystem.
- **Domain and Template contracts.** Domain reads include its name, public DKIM key and Tracking Policy. Domain PATCH replaces the full Tracking Policy. Templates have ID, Domain, title, lifetime and HTML in detail reads; list only Persistent Templates and omit HTML from list summaries. Template PATCH changes title and/or HTML, leaving omitted fields unchanged. Deleting a Template cannot change or break accepted Batches because content is frozen. Successful creation returns 201; reads and updates return their resource directly; Template deletion returns 204.
- **Unified Batch input.** Creation accepts from with email and optional name, subject, mutually exclusive content alternatives selected by type (inline html or a template_id), and recipients. Each Recipient carries email plus optional fields and Tracking Policy restriction. Other supported inputs are scheduled_at, global_fields, attachments, display headers, tracking, one_click_unsubscribe and reply_to. reply_to takes email and optional name like from, is literal rather than personalized, and is not bound to the Domain; without it no Reply-To header is emitted. Preserve the distinction between display headers and actual delivery recipients. No delivery is implied solely by a To/CC display header.
- **Personalization and immutable content.** Merge global_fields defaults with per-recipient fields taking precedence. Apply the resulting values to both HTML and subject as literal substitution values. Reserve email for the actual recipient address; it cannot be supplied as an override. Reject an affected Recipient inline when a placeholder remains unresolved. Snapshot accepted content at Batch creation, with the original Template reference retained only as provenance. Later Template edits/deletion do not affect it. Keep these new REST semantics separate from legacy gRPC behavior without duplicating the entire domain implementation.
- **Tracking and unsubscribe.** Preserve the established Domain/Batch/Recipient Tracking Policy cascade and freeze the resolved policy for each accepted Delivery. A Batch-level violation fails the request; recipient-specific violations reject only that row. One-Click Unsubscribe remains a sender-owned HTTPS endpoint template stated at Batch level, personalized per Delivery and signed into headers. Kannon does not call the endpoint, maintain suppression lists or infer consent. An invalid common endpoint fails the request; unresolved recipient substitution rejects that Recipient inline.
- **Scheduling and input limits.** Omit scheduled_at for immediate sending. If supplied, require a future timestamp at first creation and return 422 otherwise; do not rerun that check for a valid replay. Accept at most 2,000 input Recipients and a total HTTP body of 10 MiB, including attachment base64 expansion. Too many Recipients fails the whole request with 422; excessive body size returns 413. Attachments use filename and content_base64. Duplicate filenames fail the whole request with duplicate_attachment_filename rather than overwriting. Content (subject and HTML plus base64 attachments) above the configured api.max_payload fails the whole request with 422 message_too_large; a Recipient whose fields, global ones included, personalise it past that limit is refused alone with message_too_large. Never truncate input silently.
- **Address comparison.** Trim outer whitespace and lowercase only the email domain when comparing duplicates. Preserve local-part case, dots and plus-tags. The first occurrence is processed; later occurrences are inline duplicate_recipient refusals with original indexes, even if their fields differ. Two intended sends to the same address require separate Batches.
- **Intake and atomicity.** Common request errors prevent creation. Accept valid Recipients while returning individual refusals with zero-based index, stable code, field pointer and explanatory detail. If all Recipients are refused, return 422 with refusal details and create no Batch. Persist the Batch and all accepted Deliveries atomically before returning 201 and Location. An infrastructure failure must not leave a partially created Batch. Acceptance means queued responsibility, not SMTP delivery or inbox placement.
- **No inline rejection persistence.** An inline refusal never creates a Delivery, event or stored rejection record. Do not persist its address, fields or refusal details indirectly through raw request/response caches. Intake counts may be retained. The initial creation response includes rejected_recipients; clients must retain these details if needed. No separate rejections endpoint exists. Validator rejection after a Delivery exists is recorded as that Delivery's rejected outcome. SMTP refusal remains a bounce.
- **Batch-specific idempotency.** Require Idempotency-Key on Batch creation, scoped to the Domain. Use a unique constraint, transaction and minimal application-owned creation receipt, not a generic middleware response cache. Successful creation binds the key to the input and receipt for at least 24 hours from first successful creation, including future-scheduled Batches. Same key and input returns 200 with the same Batch identity and original accepted/rejected counts, without rejected_recipients. Changed content conflicts with 409. A refusal before creation leaves the key reusable for corrected input. While a concurrent creation is in progress, a duplicate receives 409 idempotency_in_progress and retry guidance; at most one Batch can be created. Every attempt is authorized anew. A lost post-commit response is recovered without another send. Replay never retries refused rows. After expiration, key reuse may create a new Batch. A fingerprint may identify input equality but must not become storage of raw refused input.
- **Read representations.** Single-resource operations return the resource directly. Lists return items and next_cursor, null at the end. Batch summaries carry identity, Domain, from, subject, timestamps, status, intake counts and Delivery state counts. Batch details additionally expose frozen content, resolved Batch Tracking Policy, unsubscribe configuration and attachment metadata, not attachment bytes. Read recipients through Delivery history. Initial creation is an intake snapshot; GET reads current state. Replay is a minimal creation receipt, not live state.
- **Lifecycle and history.** Public Batch states are pending, processing and completed. Public Delivery states are pending, scheduled, sending, delivered, rejected, bounced and failed. Completed means no remaining attempts, not that all Deliveries succeeded. Opens/clicks do not change delivery state. Late asynchronous bounces may change delivered to bounced without reopening Batch processing or restarting retention. Give Deliveries stable public identifiers and maintain simple persistent history updated by lifecycle transitions, independently of deletion from the operational pool. Initially calculate Batch state counts by queries; do not add event sourcing, a generic projection framework or synchronized duplicate counters. This does not replace the existing Stats pipeline or Domain aggregates.
- **History retention.** Keep Batch/Delivery history for a fixed 30 days after Batch processing completion. Do not expire pending or scheduled work. completed_at and expires_at are null until processing completes. Engagement does not reset the clock. Expired history returns 404. Stats events and aggregates follow their separate retention and may retain original Batch/Delivery identifiers after the referenced history has expired.
- **Stats separation and privacy.** Expose individual events separately from Domain counters following existing Stats v2 aggregate semantics. Include anonymous engagement in aggregate counters; do not require detail-event sums to match aggregates. Initial public event types are validated, rejected, delivered, bounced, failed, opened and clicked; internal transient worker error signals are not customer-facing outcomes. Preserve outcome-specific details including rejection/failure reasons, SMTP bounce information and the permanent/transient-refusal distinction. Anonymous engagement has no detail row. Pseudonymous engagement exposes no original recipient email or Delivery ID. Only Full engagement may expose IP/user-agent. Never introduce a join that defeats the existing tracking identity guarantees.
- **Stats query parameters.** Require from and to with an explicit timezone; use inclusive start and exclusive end, UTC output, and no fixed fractional-second precision. Individual events accept repeated type parameters, optional batch_id and cursor pagination. Aggregates accept group_by in Go duration syntax, require whole-hour multiples at least 1h, align from to a UTC hour and require to minus from to be a multiple of the grouping duration. Anchor complete buckets at from, return them chronologically, include zeros for empty buckets and limit a response to 1,000 buckets. Clients split requests or increase grouping for longer ranges. Zero means no counted events, not verified collection uptime. Aggregate counters remain Domain-level; there is no Batch aggregate filter.
- **Pagination.** Use limit with default 100 and maximum 1,000, plus an opaque cursor bound to Domain, collection and filters. Reject unknown query parameters, invalid values or cursor reuse with a different query using explicit 400 errors. Use fixed ordering: Domain name ascending; Template and Delivery ID ascending; Batch/API Key creation timestamp descending with ID descending as tie-breaker; event timestamp descending with ID descending as tie-breaker; aggregate buckets ascending. Use last-row positions, not persisted pagination sessions or distributed snapshots. Do not promise an immutable snapshot or require total counts on every list.
- **Error contract.** Use application/problem+json with RFC 9457 fields and stable type identifiers urn:kannon:problem:<code>. Include code and request_id, and validation errors with code, pointer and detail. Clients branch on identifiers, not human prose, and tolerate future error codes. Use 400 for malformed requests/invalid query inputs, 401 for missing/invalid credentials, 403 for insufficient authority, 404 for missing/expired resources, 409 for conflicts/in-progress idempotency, 413 for body limits, 422 for invalid content, 429 for rate limits and 5xx for service failures. Never expose infrastructure internals. Include retry guidance where meaningful, not on permanent conflicts. Inline refusals use the same stable code/pointer vocabulary inside the successful creation response.
- **Initial error vocabulary.** Request errors include malformed_request, unknown_query_parameter, invalid_query_parameter, invalid_cursor, invalid_attribution, unauthenticated, forbidden, not_found, domain_already_exists, idempotency_conflict, idempotency_in_progress, request_body_too_large, validation_failed, no_recipients_accepted, too_many_recipients, duplicate_attachment_filename, message_too_large, scheduled_at_not_future, expiry_not_future, rate_limited, internal_error and service_unavailable. Inline refusal reasons include invalid_email, duplicate_recipient, tracking_above_ceiling, unsupported_tracking_mode, unsubscribe_url_unresolved, unresolved_placeholder, reserved_field and message_too_large. Do not confuse the rejected intake count with the number of existing Deliveries later rejected by validation.
- **Health.** Public GET health requires no Bearer credential, returns 200 with minimal ready status when checks pass and 503 Problem Details otherwise, without leaking database or infrastructure error text.
- **Schema/documentation ownership.** Preserve the approved machine-readable contract and ADR decisions about shared Domain resources, immutable Batch content, retained Delivery history and separation of wire formats from domain models. Select compatible generation tooling during implementation; tooling must not force domain imports or change the agreed contract. Keep all engineering artifacts, code and tracker content in English.

## Testing Decisions

- **Confirmed test interfaces.** The user approved the complete HTTP API as the main acceptance-test interface, existing application interfaces for domain/RBAC rules, and only the missing high-level Batch creation operation as a new application test interface. Use real persistence for atomicity and concurrent retries, without inventing additional mock layers. Prefer exercising the highest meaningful interface rather than testing private helper choreography.
- **What makes a good test.** Assert externally observable responses, authorized effects, durable invariants and absence of forbidden effects. Tests should survive changes to internal helpers, repository query structure and orchestration layout. Do not assert implementation call sequences, generated boilerplate or private fields merely to mirror the code.
- **HTTP contract coverage.** Drive the mounted REST API and verify paths, methods, authentication, applicable statuses, headers, Problem Details, query parsing and response schemas. Cover all five roles and cross-Domain denial, admin-only Template/key management, public health, opaque identifiers, pagination and single/list response conventions. Verify OpenAPI validity, generated artifacts and examples stay consistent. Reject HTML/Template alternatives provided together, unknown query parameters and the 2,001st Recipient; check body size at and beyond 10 MiB.
- **Application behavior.** Reuse the existing Domain, Template, API Key and Stats operation interfaces for permission matrices and business invariants. Exercise the new Batch operation for partial/all-refused intake, snapshot independence, personalization precedence and missing placeholders, reserved email, normalized duplicates, filename collisions, scheduling and Tracking Policy/unsubscribe rules. Verify refused operations do not mutate state. Use the existing authorization Guard and audit recorder behaviors rather than a parallel testing abstraction.
- **Real-persistence integration.** Use the existing database-backed test setup to prove Batch/Delivery/receipt atomicity, rollback, unique-key enforcement, concurrent same-key requests and recovery after a committed response is lost. Verify replay yields one Batch, original counts and no inline refusal detail; different content conflicts; pre-creation failure permits correction. Ensure inline-rejected addresses/fields/details are absent from persistent Batch/Delivery/receipt storage. Testing persistence invariants is justified here; do not replace these tests with mocked transaction calls.
- **Credential compatibility.** Seed a pre-existing API Key record with no new role metadata and verify the same secret authenticates as sender only, through its existing Domain. Verify no key-row rewrite/reissuance is required. Test explicit roles, optional/future expiry, revoked/expired credentials, one-time secret disclosure, immutable roles, repeatable revocation and prevention of reactivation or cross-Domain issuance.
- **Lifecycle and time.** Drive existing worker-facing transitions and public reads to verify stable Delivery history, state counts, completion after the final pending attempt, late bounces and the distinction between delivery and engagement. Control time at the application level to test future scheduling, replay after scheduled time, 24-hour idempotency and fixed 30-day cleanup. Pending work must survive cleanup; late engagement/bounce must not restart the retention clock. Verify Stats references can outlive 404 history reads.
- **Statistics and privacy.** Test half-open ranges, identical timestamps with deterministic tie-breakers, type/Batch filters, minimum and whole-hour grouping, alignment, no partial buckets, zero-filled gaps and 1,000-bucket limits. Verify anonymous events contribute only to aggregates, pseudonymous events cannot expose original identity, and IP/user-agent require Full. Verify metrics-reader cannot obtain individual events or Delivery history. Do not infer per-Batch counters from incomplete detail events.
- **Pagination behavior.** Test complete traversal with timestamp ties, cursor reuse across filters/Domains, invalid cursor rejection and normal concurrent insertion/deletion without asserting snapshot semantics. No persisted cursor-session mechanism should be needed.
- **Prior art to reuse.** Existing application authorization tests already use principal/operation permission matrices and verify refused updates have no effect. API Key operation tests cover issuance, lookup, list, revocation and authentication. Mailer tests cover cross-Domain senders, malformed headers, frozen Tracking Policy, individual rejection and global-field behavior. Shared repository specifications already exercise multiple repository implementations, with a database-backed harness available. Existing audit tests and full-stack send/Stats clients provide the foundation for a small number of end-to-end journeys. Retain legacy regression coverage to prove the old gRPC semantics remain stable.
- **Layering checks.** Enforce that domain/application modules do not import generated REST DTOs or HTTP/Connect request types. Keep these checks narrow; do not impose a new architecture or require redundant tests of every generated accessor.

## Out of Scope

- Immediate gRPC removal, a fixed removal date, or feature parity additions to legacy gRPC.
- API Key data migration, replacement tables, existing-row backfill, copying/reissuing credentials or changing existing secrets.
- Dedicated template-editor/key-manager roles, custom role definitions, a generic delegation engine, user/session management or identity impersonation.
- Batch cancellation, rescheduling, mutable accepted content, Domain deletion/renaming, DNS verification and DKIM rotation.
- Per-Batch aggregate engagement counters, anonymous-event reconstruction, or changing existing Stats retention to match the 30-day history window.
- Persistence or later retrieval of inline rejection detail, full original-response replay, or a separate rejection-resource endpoint.
- Attachment download endpoints, bulk upload sessions, multipart sending and bypassing the 2,000-Recipient/10 MiB limits.
- Arbitrary sorting, offset/page-number pagination, mandatory totals, persistent cursor sessions or distributed snapshots.
- Event sourcing, generic projections, a new command bus, generic idempotency middleware or speculative performance caches.
- Configuration of Batch/Delivery history retention in the beta; it is fixed at 30 days.
- New webhook, suppression-list, consent-management or unsubscribe-processing features.
- A mandated Go generator or a new documentation-hosting platform; choose compatible tooling without changing the contract.

## Further Notes

This spec synthesizes the completed design interview, its final approval and the subsequent simplification review. It is the implementation specification, not a record that implementation already exists. The repository currently has the authorization engine, application modules and legacy transports, but not the new REST operations, persisted selectable roles or durable Delivery read model.

The approved machine-readable OpenAPI definition and the three design ADRs were prepared alongside the interview. Preserve them as part of delivery. Existing glossary vocabulary remains authoritative: message_id is a legacy Batch identifier, Recipient is input, Delivery is accepted per-recipient work, and Delivered means remote SMTP acceptance rather than inbox placement. Existing Domain aggregates do not have a Batch dimension; correct any stale documentation suggesting otherwise instead of expanding the scope.

The agreed reduction to five roles supersedes the earlier seven-role proposal. The agreement not to persist inline refusals supersedes the earlier exact-response replay proposal. The fixed 30-day history window supersedes the initial configurable-retention suggestion. Preserving the existing API Key table and records is mandatory even when additive role metadata is introduced.

Track this as one parent implementation specification with the ready-for-agent label. Implementation may be sliced into coherent follow-up work while preserving this contract, but this publication does not itself authorize deployment or replace the agreed design with a broader framework.
